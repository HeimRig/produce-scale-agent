# 项目定位与边界

## 一句话

一台能自己完成交易的秤：**看见是什么 → 查价 → 称重 → 算钱 → 说出来 → 打票**，闭环跑在树莓派上，能力同时暴露成 Python 工具、LLM function calling 和 MCP。

关键词：`perception → decision → action` 闭环、边缘部署、Agent 工具编排、软硬件联调。

## 与本科毕设的边界

两件事，互不依赖：

| | 本科毕设（已结题） | 本项目 |
|---|---|---|
| 定位 | 一台分类计价电子秤 | 一个边缘具身 Agent |
| 交付形态 | 全屏收银 GUI + 购物车 + 订单库 | CLI / MCP 服务 + 语音 + 小票 |
| 核心问题 | 分类准不准、称得准不准 | 怎么把感知、决策、动作串成闭环 |
| 代码关系 | 无引用、无拷贝、无共用文件 | 独立仓库，独立模型与标定 |
| 数据关系 | 自建数据集 | Fruits-360 公开数据集，按本项目类别重新训练 |

**为什么看起来像**：都是"摄像头 + 秤 + 树莓派"。但毕设做的是一块**屏幕上的收银台**，本项目做的是一个**能被其他 Agent 调用的秤**——前者终点是 GUI，后者终点是工具接口。技术上没有共享代码，同名硬件只是同一个题目域的自然选择。

## 三处值得一提的独立发现

1. **白底训练集在实拍场景直接崩**：只用 Fruits-360 白底图训练，白底验证集 97.5%，换到真实背景照片只有 38.0%。把约 700 张实拍图混进训练后，实拍从 38.0% 提到 88.5%（261 张留出），白底指标基本没退步。这是"我知道模型会在哪里失效、也验证了修法有效"的证据。
2. **INT8 量化在 MobileNetV3-Small 上会崩**：动态量化 10.3%；静态 QDQ、QOperator、只量化 Conv 三种路径与 fp32 的一致率只有 15%–20%（12 类、80 张白底验证集）。原因在 hard-swish 激活与 SE 模块对定点数敏感。最终交付 fp32（6.39 MB，PC 端 P50 2.5 ms）。这是一次"试了、掉点、改回 fp32"的完整技术判断，不是没做。
3. **量化前必须清 `value_info`**：torch 动态导出会在图里带两百多条形状注解，ONNX Runtime 的 shape inference 会报 `576 vs 1024` 冲突导致量化直接失败。`del graph.value_info[:]` 再存即可。
